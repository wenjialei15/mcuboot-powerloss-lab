为什么挑这件事做

OTA 最危险的不是下载，是写入。

下载失败可以重来，写到一半掉电，设备可能再也起不来。

工业现场、电池供电的传感器、装在杆子上的设备——没有谁会等你"升级完成再断电"。A/B 双槽存在的理由，就是让这个瞬间可恢复。

MCUboot 是这个问题的标准答案之一。但它自带的模拟器绑定 Rust + Cargo，很多嵌入式同学的机器上只有 Keil 和 GCC。

所以这里只做一件事：补上那 150 行 C，让真实的上游代码在任何有 C 编译器的机器上跑起来，然后一个点一个点地拔电。

怎么做的

没有复刻模型，跑的就是上游源码。

driver src/main.c 构造镜像、扫描断电点、断言结果
upstream boot/bootutil/*.c MCUboot 的换槽与状态机，一行未改
upstream sim/…/run.c 上游模拟器自带的 C 胶水层，setjmp/longjmp 计数
this repo port/sim_port.c 256 KB RAM Flash、扇区表、读写擦除，约 150 行
hardware 0 块开发板 一个 C 编译器即可

断电语义与上游一致：计数归零的那次擦写不会执行，等价于"在第 N 次操作之前掉电"。

结果

每个断电点检查三件事：能启动、槽内容正确、再启动不再写 Flash。

为什么每个点都能恢复

不是因为运气好，是因为顺序被设计过。

看操作序列会发现一个固定节奏：每搬完一个扇区，先往 swap status 写 8 字节进度，再动下一块数据。

erase scratch
copy 4 KB  →  scratch
write status (8 B)      ← 先记账
erase slot1
copy 4 KB  →  slot1
write status (8 B)

所以任意时刻掉电，Flash 上留下的都是一个自洽的中间态：要么"第 k 块搬完了"，要么"第 k 块还没开始"。

重启后读回 status，从 k 继续。这个状态是幂等的——重复执行同一个 k 不会破坏数据，所以重试安全。

66 次操作里，36 次在搬数据，16 次写 8 字节状态，2 次写 16 字节标记，12 次是擦除。真正让设备活下来的，是那 18 次小写入。

边界

这是验证实验台，不是"MCUboot 已通过全部认证"。

  • 只测未签名镜像（校验 SHA256），没有覆盖 ECDSA 签名路径。
  • 只覆盖 swap-scratch，没有覆盖 swap-move / overwrite-only / direct-XIP。
  • RAM 模型不模拟 NOR 的位翻转、坏块、写放大和真实擦除时间。
  • 不能替代真机的高低温、掉电时序与老化测试。

这些边界写在 README 里，也是下一步要补的：签名镜像、swap-move、以及真板上的实测。
